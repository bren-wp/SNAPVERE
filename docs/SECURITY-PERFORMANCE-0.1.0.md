# SNAPVERE 0.1.0 security and performance hardening

This document records the controls and evidence expected for the SNAPVERE 0.1.0 Windows + Android release line. It does not claim that any application can be proven free of every defect or vulnerability.

## Local-first boundary

Windows capture/editor processing remains local. The desktop runtime contains no first-party HTTP/socket client, WebView/WebView2 or JavaScript execution path. Android intentionally declares no `android.permission.INTERNET`, disables cleartext traffic and backup, and keeps the MediaProjection capture service non-exported.

Website, support and legal links are explicit user actions delegated to OS handlers; they do not introduce a background SNAPVERE networking client.

## Windows hardening retained in 0.1.0

- NuGet audit covers direct and transitive packages at `low` severity and above.
- `NU1901`–`NU1904` are treated as build failures.
- Nullable/analyzer warnings remain errors.
- Ordinary CI checkout does not persist repository credentials.
- Build/release actions are pinned to full commit SHAs.
- Setup/Portable package boundary and extraction protections remain in place.
- Portable cached payloads are verified against architecture-specific trusted SHA-256 manifests embedded in the host before execution.
- Missing, modified, unexpected or reparse-point cache content triggers transactional rebuild/revalidation.
- Capture writes use a temporary file followed by atomic move; secondary temp-file cleanup failures do not replace the original capture result.
- Capture-history and preference paths now also contain `SecurityException`/policy failures where a restricted filesystem can otherwise surface them.

The application is not represented as a sandbox against arbitrary malicious code already running as the same Windows user.

## Android lifecycle hardening

0.1.0 strengthens the existing single-capture MediaProjection session:

- foreground notification/service initialization faults are converted to a controlled capture failure;
- Handler scheduling for task-hide and first-frame work is checked;
- task-hide remains bounded to five seconds;
- first-frame delivery remains bounded to seven seconds;
- `ImageReader.acquireLatestImage()` remains guarded;
- acquired Image and Bitmap resources are deterministically released before final completion cleanup;
- MediaProjection, callback, VirtualDisplay, ImageReader and HandlerThread cleanup remains exception-safe per resource;
- only the owning service instance releases global capture ownership, reducing stale teardown races;
- conversion/provider failure and allocation failure are contained by capture cleanup rather than intentionally terminating the Activity.

## Android buffer safety

The capture reader is `RGBA_8888`. Before bitmap copy SNAPVERE validates:

- visible width > 0;
- pixel stride is exactly 4 bytes;
- positive row stride;
- row stride contains the complete visible row;
- row padding is an integer number of pixels;
- integer arithmetic for visible/padded width cannot overflow;
- ByteBuffer is rewound before copy;
- remaining buffer bytes cover `rowStride × height`.

JVM regression tests cover tight/padded rows, invalid dimensions, unexpected pixel stride, partial padding and overflow.

## Android privacy contract

Automated Android validation fails when any of the following regress:

- `android.permission.INTERNET` appears;
- cleartext becomes enabled;
- backup becomes enabled;
- MediaProjection foreground-service permission/type is removed;
- `CaptureService` becomes exported;
- Android versionName/versionCode no longer match 0.1.0 / 10.

No telemetry, analytics SDK, advertising SDK, cloud uploader, WebView or remote-control channel is part of the 0.1.0 Android source.

## Android release signing

The CI debug APK is test evidence only. Public `SNAPVERE.apk` is accepted only when the release workflow can build the minified/shrunk release variant and verify a stable private Android release signature.

Required GitHub secrets are:

- `SNAPVERE_ANDROID_KEYSTORE_BASE64`
- `SNAPVERE_ANDROID_KEY_ALIAS`
- `SNAPVERE_ANDROID_KEYSTORE_PASSWORD`
- `SNAPVERE_ANDROID_KEY_PASSWORD`

The release workflow fails before tag creation when these values are missing/invalid. It never publishes an ephemeral debug identity as the production APK.

## Source-archive integrity

`SNAPVERE-Android-Source.zip` is generated by `git archive` from the exact validated release commit's `android/` tree. The workflow verifies expected Gradle/manifest/MainActivity paths and rejects generated `build/` or `.gradle/` content.

Signing material is not part of the archive.

## Release immutability and four-asset contract

The 0.1.0 release workflow is triggered only by a dedicated `main` release-trigger change after source CI has passed. Before tag creation it rebuilds/revalidates Windows and Android deliverables.

The immutable `v0.1.0` tag is created only after all pre-publication gates pass. Tag lookup is fail-closed: only an actual HTTP 404 is treated as "tag absent". Existing annotated tags must resolve to the exact validated commit.

A valid v0.1.0 release contains exactly:

```text
SNAPVERE-Setup.exe
SNAPVERE-Portable.exe
SNAPVERE.apk
SNAPVERE-Android-Source.zip
```

The workflow records SHA-256 for all four files and post-publication verifies GitHub's asset digest against those local values. Existing releases/assets are not overwritten.

## Performance model

SNAPVERE avoids resident work that is unnecessary while idle:

- native Windows tray/hotkey message loops block instead of polling;
- capture/D3D resources are allocated for capture work, not solely because the tray process is running;
- secondary WinUI windows are on demand;
- Recent Captures discovery is bounded and local;
- Portable payload-cache verification performs sequential SHA-256 reads against the embedded manifest;
- Android creates MediaProjection/ImageReader/VirtualDisplay only for an approved capture;
- Android has no network worker, telemetry loop or continuous recorder.

The 0.1.0 changes do not loosen existing package lifecycle timeouts or visual-regression thresholds to obtain a green build.

## Automated evidence

### Windows

The release/CI gates include audited restore, x64 build/tests, x86 build, ARM64 cross-build, payload-integrity validation, six rendered WinUI surfaces, universal Setup/Portable packaging, exact asset checks and x64/x86 lifecycle/tray-first runtime probes.

### Android

CI runs debug/release lint, JVM tests and debug/release builds plus debug APK signature/alignment/digest checks. The release job additionally validates the stable release signature, Android source archive and Android artifact-transfer hashes.

### Final publication

The release job accepts publication only after both platform pipelines are valid and post-publication digest verification succeeds for all four public assets.

## Evidence boundaries

- ARM64 Windows on the hosted x64 runner is cross-build/package evidence, not physical ARM64 runtime testing.
- Android CI/release automation is not exhaustive physical-device testing across every OEM skin, display configuration, memory pressure state or permission manager.
- Security controls reduce known classes of failure; they do not constitute a universal guarantee against unknown vulnerabilities.
